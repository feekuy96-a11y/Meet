# รายงานตรวจและแก้ MeetNote TH

วันที่ตรวจ: 7 ตุลาคม 2026 — ตรวจไฟล์แนบ 11 ไฟล์ และการทำงานร่วมกันของ frontend, IndexedDB, MediaRecorder, service worker และ Google Apps Script

**ผล:** แก้ข้อบกพร่องที่ยืนยันได้และส่งมอบไฟล์ทดแทนเต็มไฟล์ พร้อมชุดทดสอบและคู่มือ ตรรกะระบบและการทำงานใน Chromium ทดสอบได้ในเครื่องนี้ แต่ยังไม่รับรองการเรียก Gemini/Apps Script/Drive บนบัญชีจริง ระบบยังใช้รหัสร่วมและข้อมูลในเบราว์เซอร์ จึงยังไม่ใช่ระบบสาธารณะหรือระบบรับประกันไม่มีปัญหาในอนาคต

## 3. หลักฐานการทดสอบ

### รันในเครื่องทดสอบจริง

- `npm ci --ignore-scripts --no-audit --no-fund --cache /workspace/.npm-cache`: ติดตั้งจาก lockfile ได้
- `npm test`: **26 ผ่าน, 0 ล้มเหลว, 0 ข้าม** (10 core, 7 backend และ 9 cloud)
- Browser smoke test บน Chromium จริงผ่าน: ข้อความอยู่หลัง reload, แก้ข้อความ, theme, URL validation, token ไม่เก็บถาวร, AI UI, ข้อความ HTML จาก error ไม่กลายเป็น tag, MediaRecorder กับไมโครโฟนจำลอง, พัก/ทำต่อ, final audio เปิด metadata ได้และดาวน์โหลด, Markdown/Word/PDF print view/JSON, import, crash recovery, quota-failure recovery, offline shell, ป้องกันแท็บที่สอง และข้อมูลเก่าเสียรูปแบบยังสำรองได้
- เส้นทางสร้าง Docs ที่เซิร์ฟเวอร์ตอบ error แล้วลองใหม่ใน browser ใช้ backend จำลอง ตรวจว่า request ID ยังเดิมหลัง reload และลิงก์ใช้ noopener/noreferrer
- API timeout/abort ทดสอบใน unit test ด้วย simulated timer ไม่ใช่การรอเซิร์ฟเวอร์จริง 90 วินาที
- ชุด backend ใช้ Apps Script service doubles ตรวจสร้างสองเอกสารครบหัวข้อ ลิงก์เสียง การสร้างซ้ำ การล้างไฟล์หลังล้มเหลว ตรวจสิทธิ์และ rate limit **ไม่ใช่การสร้างเอกสารจริงใน Google Drive**
- `npm audit --audit-level=moderate`: **0 ช่องโหว่ที่ registry รายงาน** ณ วันที่ตรวจ รวม dev dependencies ไม่ใช่หลักฐานว่าโค้ดแอปไม่มีช่องโหว่
- ตรวจ JavaScript/Code.gs syntax และรูปแบบไฟล์ผ่าน
- เปรียบเทียบไฟล์ style.css/worklet.js กับไฟล์แนบตรงทุกไบต์

### ยังไม่ได้รัน/ไม่สามารถยืนยันจากเครื่องนี้

- Deploy Apps Script และ Google Workspace policy/CORS/redirect บนบัญชีจริง
- Gemini จริง รุ่นโมเดลที่โปรเจกต์มีสิทธิ์ใช้ JSON/audio และคุณภาพการสรุปภาษาไทย
- Drive/Docs จริง สิทธิ์โฟลเดอร์ โควตา และการแชร์ที่สืบทอด
- การถอดเสียงสดผ่านบริการของ Chrome/Edge จริง (การทดสอบบันทึกเสียงปิดสวิตช์นี้)
- โทรศัพท์/iOS/Safari/Firefox การปิดจอ การพักเครื่อง หรือประชุมหลายชั่วโมง
- ความเสียหายของ disk/IndexedDB จริง หรือการลบข้อมูลเว็บไซต์โดยผู้ใช้
- การโหลด/ทดสอบภายหลัง Publish cloud environment หรือการเผยแพร่ GitHub Pages

ไม่ปิด assertion ไม่ใช้ชุดทดสอบศูนย์รายการ และไม่แทน functional checks ด้วย formatter ผลที่ผ่านคือความสามารถที่ทดสอบภายในขอบเขตข้างต้นเท่านั้น

## 4. ข้อจำกัดความปลอดภัยที่ยังมี

1. **Shared token ไม่ใช่บัญชีผู้ใช้:** ผู้มีรหัสมีอำนาจเรียก backend เท่ากัน จำกัดรายคน/เพิกถอนรายคนไม่ได้ การเพิ่ม per-user authentication ต้องเป็นงานพัฒนาสถาปัตยกรรม ไม่สามารถแก้ด้วยซ่อน URL หรือ CORS
2. **Endpoint anonymous ยังถูกยิงเพื่อกิน Apps Script execution quota ได้:** rate limit ในแอปป้องกันการเรียก Gemini/Docs ของผู้ผ่านรหัสเกิน 20 ครั้งต่อนาที ไม่ใช่การป้องกัน DDoS หรือเพดานค่าใช้จ่ายรายเดือน
3. **Apps Script ทำงานด้วยสิทธิ์เจ้าของ:** ใช้บัญชีเฉพาะและอย่าให้คนไม่ไว้ใจแก้โปรเจกต์ สิทธิ์ Drive OAuth กว้างกว่าการจำกัดโฟลเดอร์ในโค้ด
4. **ข้อมูลในเครื่องไม่ได้เข้ารหัสโดยแอป:** ผู้เข้าถึงโปรไฟล์เบราว์เซอร์/เครื่องสามารถอ่านข้อมูลได้ ใช้บัญชี OS ที่ล็อกเครื่องและดิสก์เข้ารหัสตามนโยบายองค์กร
5. **Prompt injection/AI hallucination ยังเป็นไปได้:** system prompt แยกข้อมูลจากคำสั่งและตรวจ JSON ได้ แต่ไม่รับประกันความถูกต้องของมติ ตัวบุคคล และเวลา ต้องมีมนุษย์ตรวจรายงานก่อนใช้
6. **ผู้ใช้ต้องเลือก backend ของตนเอง:** การจำกัด host ป้องกันปลายทางนอก Google แต่สคริปต์ของคนอื่นบน script.google.com ก็สามารถรับข้อมูลได้ อย่ารับ URL จากแหล่งไม่น่าเชื่อถือ
7. **สิทธิ์แชร์สืบทอด:** โฟลเดอร์ที่แชร์อยู่ทำให้ไฟล์ใหม่เข้าถึงได้ตามสิทธิ์นั้น แม้แอปไม่เรียก share เอง ต้องตรวจ Drive จริง
8. **GitHub Pages ตั้ง security headers เองได้จำกัด:** meta CSP ป้องกันการโหลด script หลายรูปแบบ แต่ไม่บังคับ frame-ancestors หากต้องป้องกัน clickjacking ครบควรเลือกโฮสต์ที่ตั้ง header ได้
9. **Dependency audit มีขอบเขต:** dev dependencies ใช้กับทดสอบ/formatter ไม่มี third-party runtime JS ที่โหลดในหน้าเว็บ แต่ต้องอัปเดต dependencies และตรวจประกาศความปลอดภัยสม่ำเสมอ

## 5. ข้อจำกัดความทนทานและแนวทางต่อยอด

- chunk ประมาณ 2 วินาทีไม่ใช่การรับประกันเวลาสูญหายสูงสุด Browser อาจพักการส่งข้อมูลและเก็บก้อนใหญ่ ถ้าปิด process ก่อน DB commit ช่วงที่ยังไม่เขียนหายได้
- queue การเขียนลดการเก็บเสียงทั้งประชุมใน RAM แต่หาก disk ช้าหรือ browser เลื่อน event มาก ยังเกิดช่วงใช้หน่วยความจำสูงได้ ต้องทดสอบประชุมระยะเวลาจริงและมีเครื่องสำรองในงานสำคัญ
- ดาวน์โหลดเสียงกู้คืนได้เมื่อ Blob ที่ล้มเหลวยังอยู่ในแท็บ และส่วนที่ DB เขียนแล้วอ่านได้ ถ้าฐานข้อมูลอ่านไม่ได้หรือเครื่องเสียหายไม่รับประกันการกู้คืน
- ประวัติ ID สร้าง Docs จำกัด 30 วัน/100 งานและพื้นที่ Script Properties ไม่ใช่ distributed transaction ระหว่าง Drive/Docs/Properties การหยุด process ระหว่างสร้างไฟล์อาจเหลือไฟล์ตกค้าง ให้ผู้ดูแลตรวจ JOB และ Drive แทนการสร้างซ้ำโดยเดา
- JSON ไม่รวมเสียงและยังไม่มีการนำเข้าเสียง ไม่ใช่ backup แบบครบทุกไฟล์ ต้องสำรองเสียงแยก
- ประวัติในเครื่องอยู่ตาม origin/เบราว์เซอร์ รุ่น 3 เลือกซิงก์ผ่าน Drive ได้ตาม SYNC_TH.md การขอ persistent storage อาจไม่ได้รับอนุญาตและไม่แทนการสำรอง

ลำดับต่อยอดที่แนะนำเมื่อจะใช้งานวงกว้าง:

1. ระบบผู้ใช้/สิทธิ์รายคน และ secret management ที่แยกสิทธิ์
2. backend ที่มี durable job queue, storage ของเสียง, quota และ audit log โดยไม่เก็บเนื้อหาหรือ token ใน log
3. backup/restore รวมข้อความและเสียง พร้อมตรวจ checksum/จำนวนช่วงและทดสอบ restore
4. transcription/diarization service จริงที่มีคำยินยอม ขอบเขตความแม่นยำ และวิธีแก้ข้อมูล
5. ทดสอบโหลด ระยะเวลายาว เครือข่ายหลุด อุปกรณ์มือถือ และการอัปเกรดฐานข้อมูล

ติดตั้งและผ่าน checklist บัญชี/อุปกรณ์จริงใน `INSTALL_TH.md` ก่อนใช้ข้อมูลสำคัญ โค้ดรุ่นก่อนส่งขึ้น GitHub แล้ว การทดสอบ Google ใช้ระบบจำลอง ไม่ได้ส่งข้อความ/เสียงประชุมจริงไป Google
